# 01 カリキュラム — 何を勉強するか

5つのトラックに分ける。並行で進めるが 週によって重心を変える（配分は `03_スケジュール_12週.md`）。

教材は「これ1冊」ではなく 各トラックで**主教材1つ＋参照1〜2つ**。読み切ることが目的ではなく 製品作りで詰まったときに引ける状態を作る。

---

## Track A 言語と実装力（TypeScript / Node / SQL）

一番時間を割く。AIが書いたコードを「読める」から「自分で書ける・直せる」に上げる。

### A-1 TypeScript を型から理解する（第1〜4週）

| 学ぶこと | 到達点 |
|---|---|
| 型システムの基礎（union / intersection / literal / narrowing） | `unknown` から安全に絞り込める |
| ジェネリクスと条件型 | ライブラリの型定義（Zod や Drizzle）が読める |
| 非同期（Promise / async-await / エラー伝播） | `try/catch` の置き場所を説明できる |
| モジュール設計（export の粒度 循環参照の回避） | 6,100行の `index.ts` をどう割るか判断できる |
| tsconfig の主要項目（strict / noUncheckedIndexedAccess / paths） | 自分で設定を書ける |

主教材
- 『プロを目指す人のためのTypeScript入門』uhyo（技術評論社）。日本語で一番体系的。第1〜4週で通読
- TypeScript Handbook（typescriptlang.org/docs/handbook）。辞書として

参照
- Total TypeScript（totaltypescript.com）。無料の Beginner's TypeScript と型演習
- type-challenges（github.com/type-challenges/type-challenges）。easy を20問。ジェネリクスの筋トレ
- 『Effective TypeScript』Dan Vanderkam（O'Reilly）。第5週以降に拾い読み

### A-2 Node とバックエンドの土台（第2〜5週）

| 学ぶこと | 到達点 |
|---|---|
| イベントループとストリーム | 「なぜここで await が要るか」を説明できる |
| HTTP の基本（ステータス ヘッダ CORS 認証ヘッダ） | 元町Cal の契約テストで見ていたものを自分で設計できる |
| 軽量フレームワーク1つ（Hono） | Cloudflare Workers と Node の両方で同じコードを動かせる |
| バリデーション（Zod） | 入口で型を確定させる設計が書ける |
| 環境変数と秘密の扱い | ローカル / staging / 本番を分離できる |

主教材
- Hono 公式ドキュメント（hono.dev）。Cloudflare Workers を既に使っているので相性がいい
- Node.js 公式ドキュメントの Guides

参照
- 『Node.jsデザインパターン 第2版』（O'Reilly Japan）。第1〜3章とストリームの章だけ

### A-3 SQL と Postgres（第3〜6週）

Firebase の Realtime Database しか使っていないのがいまの穴。案件では RDB が前提。

| 学ぶこと | 到達点 |
|---|---|
| SELECT / JOIN / GROUP BY / サブクエリ | 手で書ける |
| インデックスと実行計画 | `EXPLAIN` を読んで遅い理由を言える |
| トランザクションと分離レベル | 二重登録をどう防ぐか設計できる |
| マイグレーション | スキーマ変更を安全に本番へ出せる |
| ORM（Drizzle） | 生SQLとORMの境目を判断できる |

主教材
- SQLBolt（sqlbolt.com）。第3週に2時間で全部やる
- Use The Index, Luke（use-the-index-luke.com 日本語版あり）。インデックスの章
- Drizzle ORM 公式ドキュメント

環境
- Neon か Supabase の無料枠で Postgres を1つ持つ。ローカルは Docker

## Track B 設計力

案件票の「設計」はここ。AIは実装は速いが設計判断は人が持つ。**QAの経験がそのまま効くトラック**でもある。壊れ方を知っている人は 壊れない設計を選べる。

### B-1 コードの設計（第4〜8週）

| 学ぶこと | 到達点 |
|---|---|
| 責務の分割（モジュール 層 境界） | 「この関数はどこに置くべきか」に理由をつけて答えられる |
| 依存の向き（外側から内側へ） | DB や外部API をテストで差し替えられる構造にできる |
| エラー設計（例外か戻り値か どこで握るか） | ユーザーに見せるエラーと内部のエラーを分けられる |
| リファクタリングの手順 | テストを先に当ててから小さく直せる |

主教材
- 『リファクタリング 第2版』Martin Fowler（オーム社）。**例が JavaScript** なので相性がいい。第1章を第4週に 以降はカタログとして引く
- 『A Philosophy of Software Design』John Ousterhout（英語）。薄い。「深いモジュール」の章だけでも

参照
- 『Good Code, Bad Code』Tom Long（秀和システム）。レビュー観点の言語化に

### B-2 データと API の設計（第5〜7週）

| 学ぶこと | 到達点 |
|---|---|
| データモデリング（正規化 ID の設計 削除の扱い） | ER図を自分で書ける |
| API 設計（リソース 命名 ページング 冪等性 バージョン） | 契約を先に書いてから実装できる |
| 認証と認可（セッション JWT OAuth 権限モデル） | 「誰が何をできるか」を表にしてコードに落とせる |
| 状態管理（サーバー状態とUI状態の分離） | React で「どこに state を置くか」を決められる |

主教材
- Next.js Learn（nextjs.org/learn）。App Router / Server Actions / データ取得。第5週に通す
- Auth.js（authjs.dev）か Clerk のドキュメント。どちらかを製品で使う

### B-3 システム設計の基礎（第9〜11週）

面接で「この製品のアーキテクチャを説明して」に答えるため。

| 学ぶこと | 到達点 |
|---|---|
| スケールの考え方（キャッシュ キュー 非同期処理） | 「いまは要らないが将来はこう」を言える |
| 信頼性（リトライ タイムアウト べき等 バックオフ） | Mood-Ring の通知配信を例に説明できる |
| 観測（ログ メトリクス トレース） | 何を出せば障害を追えるか設計できる |

主教材
- 『システム設計の面接試験』Alex Xu（ソシム）。第1〜4章と 通知システムの章
- 『データ指向アプリケーションデザイン』Kleppmann（O'Reilly Japan）。第1〜3章と第7章だけ。全部読まない

## Track C 運用と品質

QAの延長で一番得意になれる領域。案件では「CI/CD を整えた」「監視を入れた」が評価される。

### C-1 チーム前提の Git（第1〜3週）

いまは一人リポジトリ。案件では PR とレビューが前提。

| 学ぶこと | 到達点 |
|---|---|
| ブランチ戦略（trunk-based / feature branch） | 自分で選んで理由を言える |
| PR の作法（小さく 説明を書く レビューを受ける） | 他人が読める PR を出せる |
| rebase / squash / cherry-pick / bisect | 履歴を整えられる。`bisect` で回帰の原因コミットを探せる |
| コンフリクトの解消 | 怖くない |

主教材
- Pro Git 日本語版（git-scm.com/book/ja/v2）。第2〜3章と第7章の rebase / bisect

### C-2 CI/CD と環境（第6〜8週）

| 学ぶこと | 到達点 |
|---|---|
| GitHub Actions（lint / test / build / deploy） | 自分で yml を書ける。Mood-Ring の CI は既にあるので Web 版を作る |
| 環境分離（preview / staging / production） | Vercel の Preview Deployment を使いこなす |
| 秘密の管理 | `.env` をリポジトリに入れない仕組みを作れる |
| マイグレーションの運用 | 本番のスキーマ変更を CI から安全に流せる |

主教材
- GitHub Actions 公式ドキュメント
- Vercel 公式ドキュメント（Environments / Preview）

### C-3 観測とデバッグ（第9〜10週）

| 学ぶこと | 到達点 |
|---|---|
| 構造化ログ | 何を出すか 何を出さないか（秘密を出さない） |
| エラー監視（Sentry） | 本番のエラーに気づける |
| デバッガ（VS Code の breakpoint / Node inspect） | `console.log` 以外で追える |
| プロファイリングの入口 | 遅い処理を特定できる |

主教材
- Sentry の Next.js 導入ガイド
- VS Code の JavaScript debugger ドキュメント

## Track D AI駆動開発の方法論

ここは**すでに実績がある**トラック。やることは「自分の運用を業界の言葉で言い直して 他人に渡せる形にする」。案件では「AI活用のプロセスを持ち込める人」として売る材料になる。

| 学ぶこと | 到達点 |
|---|---|
| 仕様駆動開発（Spec-Driven Development） | 仕様 → 計画 → タスク → 実装 の流れを自分の製品で回して文書化する |
| AGENTS.md / CLAUDE.md の書き方 | 他人のリポジトリに入って1日で書ける |
| 受け入れ基準の数値化（既にやっている） | テンプレート化して配れる |
| AIに任せる領域と人が持つ領域の線引き（既にやっている） | 案件の初日に提示できる1枚にする |
| コンテキストの管理（何を読ませ 何を読ませないか） | トークンと精度のトレードオフを説明できる |

主教材
- Claude Code 公式ドキュメント（code.claude.com/docs）。特に Best practices と Memory
- Anthropic のエンジニアリング記事「Claude Code: Best practices for agentic coding」
- GitHub Spec Kit（github.com/github/spec-kit）。仕様駆動の型を借りる
- agents.md（AGENTS.md の慣習）

成果物
- 自分の「AI駆動開発の運用手引き」を1本書く。面接と案件初日の両方で使う。既にある `operating-model.md` と qa.md の役割定義を一般化する

## Track E 選考対策

第10週から。ただし**毎日のドリルは第1週から**。

| 種類 | 対策 |
|---|---|
| コーディング試験（Surge AI は2時間） | 時間を計って中規模の課題を実装しテストまで書く練習を3回 |
| アルゴリズム（LeetCode / AtCoder） | easy〜medium を毎日1問。AtCoder ABC は土曜21時に参加（任意） |
| 設計面接 | 自分の製品を口頭で説明する練習。図を描きながら15分 |
| コードレビュー面接 | AIが書いた PR を声に出してレビューする練習 |
| 職務経歴の話し方 | `interview/` のファイルが既にある。製品の実績を足す |

主教材
- Exercism の TypeScript トラック（exercism.org）。第1〜3週。無料でメンター付き
- LeetCode（TypeScript 対応）。第4週以降
- AtCoder（atcoder.jp）。日本語で 土曜の夜に定期開催
