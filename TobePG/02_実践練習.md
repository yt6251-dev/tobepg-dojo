## P2 自分の製品を読み切る 📖→🧑（第1〜2週）

元町Cal の `index.ts` 6,118行を全部読む。成果物は **138エンドポイントの表**（名前 役割 触るデータ 認証の有無）と **モジュール境界の図**。Dojo の証拠つき課題として提出する。

## P3 Dojo の課題を解く（第1〜4週）

| 週 | 課題の出どころ | 内容 |

## P4 Dojo を育てる 🤝（第5〜10週）— 製品作り

Dojo 自体の機能追加が 各週の課題になる。

| 週 | 足す機能 | 学ぶこと | 合格条件 |
|---|---|---|---|
| 5 | `SPEC.md` `AGENTS.md`。FSO Part 13 で Postgres と Drizzle を学ぶ | 仕様駆動 RDB | 仕様に受け入れ基準が数値で書いてある |
| 6 | `results.json` → Neon + Drizzle。ダッシュボードを DB 読みに | マイグレーション ER 図 | 旧 JSON と DB の内容が一致するテスト |
| 7 | Software Design by Example「テストフレームワーク」の章 → 採点器を自作（vitest 依存を外す） | テストランナーの仕組み | 自作ランナーで 01〜05 が同じ結果 |
| 8 | GitHub ログイン（Auth.js）。CI（GitHub Actions）から結果を POST。Vercel に公開 | 認証 API 設計 CI/CD | 公開 URL で自分の進捗が見える |
| 9 | **空テスト検出**（TestLens）: アサーション無し / 常に真 / 全部モック / 同値だけ を AST で拾う | 静的解析 | 元町Cal と Mood-Ring のテストで既知の空テストを拾う |
| 10 | 判定に Claude API を足す（構造化出力）。Playwright E2E 5本。Sentry。README 英日。デモ動画 | LLM 統合 E2E | Vitest 50件 E2E 5本 CI 緑 |

核の判定ロジック（第7・9週）は 🧑 自分で書く。スキャフォールドと yml は 🤝。自分で書いた行数 **1,500行以上**。
